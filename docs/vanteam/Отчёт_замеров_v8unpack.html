Замеры и приёмка v8unpack-accel 2.0.0

Что и как измерено при выпуске 2.0.0. Две версии сравнивались на одних и тех же файлах, на одной машине, с чередованием прогонов. Результат распаковки сверялся побайтно с 1.0.0, со штатным v8unpack и с эталонной распаковкой УТ 11.5.

1. Методика

МашинаWindows 11, 4 физических / 8 логических ядер, ОЗУ 35 ГиБ; Python 3.11.8, v8unpack 1.2.13, psutil 7.0.0
Фонрабочая машина; чужие процессы (редактор, сборки, проверки кода) занимали 60–100% CPU всё время замеров. Поэтому время по часам (wall) недостоверно, сравнение — по CPU
МетрикаCPU процесса распаковки: user + kernel (psutil), по этапам — через обёртки вокруг четырёх проходов extract. Все варианты серийные, один процесс, приоритет BelowNormal
Порядокпарный замер с чередованием: варианты по очереди, в нечётных раундах прямой порядок, в чётных обратный; каждый прогон — отдельный процесс; медиана по раундам
Результатманифест каждого прогона: sha256 всех файлов и список каталогов; tree_sha — хеш отсортированного манифеста. Одинаковый tree_sha — побайтно одинаковое дерево
Антивируспроверка файлов антивирусом в реальном времени на машине замеров была выключена; контрольный замер 28.09 шёл с включённой
ФайлыComplexBitrix24_RU_UNF.cfe — расширение 3 МБ → 1483 файла, 598 каталогов, 30 946 055 байт; 1Cv8-ут-11.5.27.93-.cf — УТ 11.5, 883 МБ → 68 177 файлов; decode_stage_1 двух распаковок УНФ 3.0.14 для сверки разбора

dummy.zip — второй контейнер .cf, который v8unpack при каждой распаковке пересобирает через shutil.make_archive. В записях архива стоит время распаковки, поэтому его хеш разный при любой версии. Сверка сравнивает имена, CRC и байты записей — они совпали.

Дерево результата во всех 35 прогонах одно и то же (1483 файла, 598 каталогов, 30 946 055 байт, tree_sha 9539208d0b4b…) — в том числе с любым выключенным ускорением. Оно же было у штатного v8unpack и у 1.0.0 в контрольном замере 28.09.

Для сравнения — контрольный замер 28.09 (машина тоже загружена, защита в реальном времени включена): штатный v8unpack -E с параллельным пулом — медиана 33,46 с CPU всего дерева процессов и 218 МБ памяти, 1.0.0 — 23,51 с и 36 МБ (CPU −30%, память −84%).

5. УТ 11.5 целиком

Полная распаковка 1Cv8-ут-11.5.27.93-.cf (883 МБ). 1.0.0 — прогон 28.09 по журналу ut_err.log. Парный повтор 1.0.0 не делался: версия копирует результат, и в пике на D: не хватило бы места рядом с тремя временными каталогами. Условия прогонов разные, поэтому это ориентир, а не контрольный опыт.

8. Антивирус и время ядра

Около половины CPU распаковки — время ядра Windows. В отчёте 28.09 его приписывали проверке антивирусом. Проверка 29.09 это не подтвердила:

  • Защита в реальном времени была выключена, а доля ядра у 1.0.0 осталась прежней — 41–46% против 43–47% при включённой защите.
  • Исключённая и обычная папка на одном диске дали одинаковый результат. По 3 раунда: 1.0.0 — 26,45 и 26,72 с CPU, прототип 2.0.0 (все ускорения, кроме пропуска перезаписи) — 9,19 и 8,97 с. Разница в пределах шума.
  • Процесс антивируса MsMpEng за прогон CPU не набирает.

Проверку файлов антивирус делает в своём процессе, а распаковка её только ждёт. Это видно по времени по часам и CPU антивируса, а не по CPU распаковки. Время ядра — сами открытия, записи и закрытия файлов, и 2.0.0 снижает его только тем, что делает этих операций меньше. Исключения антивируса для temp и результата полезны, когда защита в реальном времени включена: они снимают ожидание проверки файлов.

9. Сборка

Сборка .cfe из распакованного дерева (v8unpack.build), 3 раунда: CPU 12,16 → 10,84 с (−11%) только от записи JSON и кэша каталогов; этап «Собираем код» −27%. Побайтно сверить собранный файл нельзя: v8unpack пишет в файл versions новые uuid4() при каждой сборке, размер .cfe от прогона к прогону плавает на десятки байт. Размер куска zlib (512 Б против 1 МБ) не меняет ни байты, ни CPU заметно.

Под профилировщиком cProfile сборка показывала 24% собственного времени в OrganizerCode.pack_file. Это артефакт: в Python 3.11 под профилировщиком строка не расширяется на месте, и склейка s += ... становится квадратичной. 80 тыс. склеек — 1,4 с без профилировщика и 80 с под ним. Без профилировщика тот же цикл на всех 287 модулях идёт 0,28 с.

10. Что не проверено

  • Свободная машина. Все замеры шли на фоне 60–100% чужой нагрузки. CPU от этого тоже плывёт: 1.0.0 на одном и том же файле — 17,8–28,6 с в разных сериях. Выводы делаются по медианам внутри одной серии с чередованием.
  • УТ 11.5 на 1.0.0 заново. «Было» — журнал 28.09, не парный прогон.
  • Ограниченный параллелизм. Не проверялся: на загруженной машине он не даёт выигрыша (замер 28.09: +24% CPU при 4 процессах).
  • Антивирус. Эффект исключений по времени не измерен: защита в реальном времени выключена.
  • v8unpack 1.2.6. 2.0.0 проверена только на 1.2.13.

11. Как воспроизвести

rem сверка разбора с исходным v8unpack
python tools\v8unpack_fastparse_check.py "<TEMP>\tmpXXXX\decode_stage_1" 400

rem парный замер с чередованием: 1.0.0, 2.0.0 и 2.0.0 без каждого ускорения
python bench\scripts\bench_pair.py <файл.cfe> <рабочий_каталог> 5 summary.json ^
    v1.0.0=releases\v8unpack-accel\v1.0.0\tools v2.0.0=tools ^
    без_fastbrace=tools:fastbrace без_inplace=tools:inplace без_jsonwrite=tools:jsonwrite ^
    без_io=tools:io без_accum=tools:accum

rem полная распаковка и сверка с эталонным деревом
python bench\scripts\run_variant.py tools <файл.cf> <out> <temp> result.json
python bench\scripts\compare_tree.py result.json <эталонный_каталог> compare.json

rem поставки: хеши, патчи поверх 1.0.0, рабочая копия
python releases\v8unpack-accel\verify_release.py --replay --working
