1. Зачем

Чтобы разобрать доработки клиента, нужен исходный код конфигурации и расширений. Конфигуратор для этого тяжёл: нужна база, загрузка файла и выгрузка в XML. v8unpack -E превращает бинарный .cf, .cfe или .epf в дерево JSON и BSL с понятными именами без платформы 1С. Для чтения кода и поиска доработок этого достаточно.

На расширениях по несколько мегабайт штатный v8unpack работает. На типовых конфигурациях в 0,8–1,7 ГБ он падал на гонках Windows, зависал на опции descent или вставал на третьем проходе с прогнозом в сотни часов. Ниже — что именно мешало и как это обошли.

Плюс эксплуатационные правила: временный каталог (TEMP, TMP, TMPDIR) переносится на диск с запасом до импорта v8unpack. Целевая папка и temp исключаются из антивируса и индексации Windows. Перед распаковкой целостность .cf проверяет check_cf.py. Долгий прогон запускается отделённо через WMI.

3. Главное ускорение: разбор длинных строк

Формат контейнера 1С — скобочный текст. Тексты модулей форм и длинные описания лежат в нём строками по мегабайту и больше. Разборщик v8unpack накапливал такую строку так:

self.current_value += value   # value — один символ

Левый операнд живёт в атрибуте объекта, у строки две ссылки, и CPython не может дописать её на месте: на каждый символ создаётся новая строка и копируется вся накопленная. Время растёт квадратично от длины.

Патч сохраняет автомат разбора и меняет только способ накопления:

current = self.current_value
self.current_value = None   # у строки остаётся одна ссылка
current += value            # CPython расширяет её на месте
self.current_value = current

В режиме чтения строки текст до ближайшей кавычки берётся одним куском через str.find, а не циклом по символам. Эквивалентность проверяет v8unpack_fastparse_check.py: 400 случайных файлов decode_stage_1, расхождений нет, исключения совпадают. Проверено на v8unpack 1.2.6 и 1.2.13.

Перепроверка 29.09 на самой тяжёлой форме УНФ (2 МБ): исходный разборщик — 537 с CPU, с этим патчем (1.0.0) — 0,53 с. В 2.0.0 разбор идёт уже не посимвольно, а через json.loads: 0,06 с на ту же форму (раздел 8).

8. Ускорения 2.0.0 и что ещё можно ускорить

После 1.0.0 распаковка упиралась уже не в одну квадратичную строку, а в сумму трёх вещей. Первая — посимвольный автомат разбора на Python. Вторая — запись JSON кусками по нескольку байт. Третья — десятки тысяч лишних файловых операций: запись, переименование, повторное чтение, копирование. Контрольный замер 28.09 и анализ исходников 29.09 нашли восемь мест. Все они вошли в 2.0.0 отдельными модулями, каждый проверен на побайтное совпадение результата.

Как json.loads разбирает скобочный формат

Правила автомата v8unpack в основном режиме короткие:

  • объект открывает только { в начале строки;
  • значение — всё между , и }, кавычки остаются частью значения;
  • пустое значение сразу после } не добавляется.

Строки с удвоенными кавычками выделяются чётностью: text.split('"') даёт чередование «вне строки / внутри строки». Во фрагментах «вне» разделители превращаются в скобки и кавычки JSON, фрагменты «внутри» экранируются и склеиваются обратно через \". Всё это делают C-функции над целыми строками, Python-цикла по символам нет.

Base64-картинки в формах и текстовые файлы воспроизведены отдельно. Файл целиком из base64, объект сразу после } без запятой, пустые строки и любая ошибка json.loads уходят в исходный автомат — результат тот же, просто медленнее. Такие файлы — около 2% всех файлов decode_stage_1.

9. Ограничения

  • .cf через v8unpack обратно не собирается — только Конфигуратор. v8unpack меняет только BSL и текст, структуру форм и метаданных — нет.
  • Версия 2.0.0 проверена на v8unpack 1.2.13. При обновлении v8unpack нужно повторить сверку разбора (v8unpack_fastparse_check.py, 400 файлов) и полную распаковку контрольного файла со сравнением дерева. Если что-то разошлось, ускорение выключается V8UNPACK_DISABLE.
  • Имена файлов зависят от версии v8unpack: 1.2.6 писала CommonModule.obj.100.bsl, 1.2.13 — без .100. Старые и новые деревья по путям напрямую не сравниваются.
  • dummy.zip (второй контейнер .cf) v8unpack пересобирает при каждой распаковке: содержимое то же, время в записях архива — нет. Хеш этого файла от прогона к прогону разный при любой версии.
  • Организатор без копирования работает, только когда temp и результат на одном томе; иначе — штатное копирование. С index или descent — тоже штатный путь.
  • Серийный режим надёжен, но использует одно ядро. Ограниченный параллелизм не проверялся на свободной машине (раздел 8).
  • Пик памяти 2.0.0 на УТ 11.5 — около 1 ГБ, вероятно, из-за разбора в памяти вложенных контейнеров и крупных файлов (у 1.0.0 на УТ не замерялся). На расширениях — десятки мегабайт, как у 1.0.0.
  • Дерево результата в 3–4 раза больше исходного .cf, ещё несколько гигабайт занимает temp.
