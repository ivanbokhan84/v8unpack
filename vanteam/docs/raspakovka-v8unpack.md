# Распаковка/сборка 1С через v8unpack (без Конфигуратора)

Инструмент: `v8unpack` (Python, `pip install v8unpack`, https://github.com/saby-integration/v8unpack). Проверено на **1.2.13**
(обёртки 1.0.0 — ещё и на 1.2.6). Поддерживает `.cf`, `.cfe`, `.epf`. Обёртки этого проекта — **v8unpack-accel 2.0.0**
(`tools/`, поставки — `releases/v8unpack-accel/`, изменения — `CHANGELOG.md`).

## Распаковка (чтение) — используем
```
python tools/v8unpack_serial.py <файл.cf|cfe|epf> <папка_назначения>
```
- Даёт читаемое дерево `JSON + BSL` с нормальными именами (`CommonModule/<Имя>/CommonModule.obj.bsl`, `Document/<Имя>/...`).
- Штатный `v8unpack -E` работает на расширениях по несколько мегабайт; на крупных `.cf` падает на гонках Windows
  и разбирает в разы дольше — см. «Грабли».
- `--version` при распаковке не нужен; `--descent` не передавать никогда (см. грабля 1).

## Сборка обратно (round-trip) — правила
- `.epf`: `v8unpack -B <папка> <ИмяОбработки.epf>` **БЕЗ `--version`** (иначе клиент не открывает). Перед `-B` обязательно `oscript -check` модулей (битый BSL при сборке не выявится, упадёт у клиента).
- **`.cf` через v8unpack НЕ собираем — тупик.** Только Конфигуратор.
- v8unpack меняет **только BSL**, не структуру форм (реквизиты/кнопки/поля) — структура форм только через Конфигуратор/EDT.
- Сборка недетерминирована: v8unpack пишет в файл `versions` новые `uuid4()` при каждой сборке, два `.cfe` из одного дерева
  побайтно различаются. Сравнивать содержимое, а не хеш файла.

## Обход бага v8unpack на текстовом потоке (важно)
Расширение коннектора Битрикс24 для УТ штатным v8unpack 1.2.6 **не распаковывалось**: падало в `decode_stage_1` на одном объекте
(и плоско, и с `--descent`, и с `--version`). Причина — баг в `JsonContainerDecoder.decode_file`: поток, закончившийся в режиме
`READ_TEXT_FILE`, это валидный текстовый файл (содержимое уже в `self.data`), но код бросает исключение и роняет всю распаковку.

**Решение — своя обёртка (пакет не трогаем):** monkey-patch `decode_file`, чтобы при `READ_TEXT_FILE` возвращать `self.data`.
В 1.2.13 баг НЕ исправлен — то же `raise` при `self.mode != Mode.READ_PARAM`, обёртка по-прежнему обязательна.

## Чем распаковывать

| Файл | Что делает | Когда |
|---|---|---|
| `tools/run_unpack.py` | лаунчер: TEMP рядом с результатом до импорта, зашитые пути, замер времени; патчи берёт импортом `v8unpack_serial` | **крупные `.cf`** (сотни МБ и больше) |
| `tools/v8unpack_serial.py` | серийный пул, ретраи WinError 32/5, толерантный `decode_file`, пониженный приоритет; подключает все ускорения | `.cf` / `.cfe` / `.epf` из командной строки |
| `tools/v8unpack_fastparse.py` | автомат разбора: длинные строки и значения вне кавычек куском | подключается автоматически |
| `tools/v8unpack_accum.py` | склейки строк через список: base64, текстовые файлы, раскладка модулей | подключается автоматически |
| `tools/v8unpack_fastbrace.py` | разбор скобочного формата через `json.loads`, необычное — исходному автомату | подключается автоматически |
| `tools/v8unpack_jsonwrite.py` | запись JSON своим сериализатором одной строкой | подключается автоматически |
| `tools/v8unpack_io.py` | вложенные контейнеры в памяти, кэш каталогов | подключается автоматически |
| `tools/v8unpack_organizer.py` | организатор без копирования `decode_stage_3` | подключается автоматически |
| `tools/v8unpack_newtypes.py` | неизвестные виды метаданных (`PaletteColor`, платформа 8.5.1) | подключается автоматически |
| `tools/v8unpack_resume.py` | продолжение с третьего прохода + журнал медленных объектов | после обрыва; требует `psutil` |
| `tools/v8unpack_fastparse_check.py` | сверка всей цепочки разбора с исходным `JsonContainerDecoder` | после обновления v8unpack |
| `tools/check_cf.py` | проверка целостности контейнера | перед распаковкой крупного файла |

```
python tools/check_cf.py "<src.cf>"
python tools/run_unpack.py "<src.cf>" "<out_dir>" "<temp_dir>"
python tools/v8unpack_serial.py "<src.cfe>" "<out_dir>"
python tools/v8unpack_resume.py "<TEMP>\tmpXXXX" "<out_dir>" "<журнал>"
python tools/v8unpack_fastparse_check.py "<TEMP>\tmpXXXX\decode_stage_1" 400
```

Любое ускорение выключается переменной окружения `V8UNPACK_DISABLE` (через запятую: `fastparse`, `accum`, `fastbrace`,
`jsonwrite`, `io`, `inplace`), например `set V8UNPACK_DISABLE=fastbrace,inplace`. Результат при любом наборе побайтно
одинаковый; первая строка вывода показывает версию и включённые ускорения.

Устаревшие обёртки `v8patch_unpack.py` и `v8unpack_robust.py` (параллельный пул, `descent=100` по умолчанию) в некоторых
проектах ещё лежат — **не применять**: на крупных контейнерах встают на O(N²).

## Сколько это занимает (v8unpack-accel 2.0.0, v8unpack 1.2.13)

| Что | 1.0.0 | 2.0.0 |

| УТ 11.5.27.93, 883 МБ → 68 177 файлов | 46,5 мин (журнал 28.09) | **8 мин 25 с** (29.09), дерево побайтно то же |
| — из них организатор («Организуем код») | 29 мин | 31 с |
| Расширение 3 МБ → 1483 файла, CPU (медиана 5 раундов с чередованием) | 20,98 с | 6,62 с (−68%) |
| Тяжёлая форма 2 МБ, разбор (исходный v8unpack — 537 с CPU) | 0,53 с | 0,06 с |

Замеры шли на рабочей машине с фоновой нагрузкой; методика и все цифры — `Отчёт_замеров_v8unpack.html`.

## Грабли, из-за которых распаковка встаёт

1. **`descent` — это НЕ глубина.** Номер версии файла для инкрементальной git-сборки. Любое значение включает режим `OrganizerFileCE` с побайтным сравнением O(N²): на крупном контейнере распаковка встаёт, содержимое при этом то же. Вызывать `extract(src, dst)` без опции.
2. **Гонки Windows при параллельном пуле:** `WinError 32` (sharing violation при `os.rename`), `WinError 5` (access denied, драйвер-фильтр антивируса), `WinError 87` (сбой пула после падения воркера). Лечится серийным пулом плюс ретраями `os.replace` / `os.remove` на WinError 32/5. В 2.0.0 вложенные контейнеры распаковываются в памяти, и переименований сразу после записи больше нет.
3. **Временный каталог.** Распаковка создаёт тысячи временных каталогов — выносить `TEMP`/`TMP`/`TMPDIR` на диск с запасом места, до импорта `v8unpack`. **Temp и результат — на одном томе:** тогда организатор 2.0.0 переносит `decode_stage_3` в результат одним переименованием, без копирования (`run_unpack.py` по умолчанию кладёт temp рядом с результатом). Исключения антивируса для temp и результата помогают, только когда включена защита в реальном времени; время ядра Windows (~45% CPU распаковки) — это сами файловые операции, а не проверка антивирусом.
4. **Квадратичный разбор длинных строк** (`JsonContainerDecoder._add_to_current_value`): строка копится посимвольно в атрибут объекта, и CPython копирует её целиком на каждый символ. Крупные формы разбирались по 100–500 секунд каждая, третий проход вставал с прогнозом в сотни часов. Симптом: память процесса мала (~50 МБ), а `py-spy dump` стоит в `_add_to_current_value`. Фикс — `v8unpack_fastparse.py` (1.0.0) и `v8unpack_fastbrace.py` (2.0.0). Тяжёлая форма 2 МБ: исходный разбор 537 с CPU, 1.0.0 — 0,53 с, 2.0.0 — 0,06 с; результат тот же.
5. **Квадратичная раскладка модулей** (`OrganizerCode.unpack`): модуль копится в строке внутри словаря — полная копия на каждую строку модуля. Модуль 3,2 МБ — 30 с. Фикс — `v8unpack_accum.py`: куски в списке, одна склейка.
6. **Пониженный приоритет молча не ставился:** `SetPriorityClass(GetCurrentProcess())` через ctypes без `restype`/`argtypes` передаёт псевдодескриптор 32-битным числом, вызов возвращает 0. Исправлено явными типами `c_void_p`.
7. **Неизвестные виды метаданных.** Объекты типа `PaletteColor` (GUID `102f6202-…`, платформа 8.5.1) v8unpack пропускает с сообщением «неизвестный тип вложенных метаданных». `v8unpack_newtypes.py` регистрирует их на лету.
8. **Профилировщик врёт про `+=`.** Под cProfile в Python 3.11 строка не расширяется на месте: функции со склейкой `s += ...` в профиле выглядят в десятки раз тяжелее, чем есть. Горячие точки проверять замером без профилировщика.

## Обрыв на третьем проходе

Проходы: извлечение контейнера → `decode_stage_1` → «Разбираем вложенные объекты» → «Организуем код». Если оборвалось на третьем, первые два повторять не нужно — `decode_stage_1` во временном каталоге уже готов:

```
python tools/v8unpack_resume.py "<TEMP>\tmpXXXX" "<out_dir>" "<журнал>"
```

В журнал пишутся объекты дольше 2 секунд и память процесса каждые 100 объектов — сразу видно, на чём тормозит.
Перенос `decode_stage_3` организатором 2.0.0 продолжению не мешает: `resume` строит `decode_stage_3` заново из `decode_stage_1`.

Перед распаковкой крупного контейнера — проверка целостности: `python tools/check_cf.py "<путь к .cf>"`. Вердикт `ПОВРЕЖДЁН` — распаковку не начинать, забрать файл заново.

**Замеры 1.0.0 на соседних проектах.** Типовая бухгалтерия 264 МБ (дерево 1,7 ГБ) — серийный режим без fastparse, v8unpack 1.2.6: 1 ч 27 мин, без ошибок; один объект обрабатывался 26 минут. Параллельный режим на том же файле падал на гонках. УНФ 3.0.14.159, 1 ГБ — с fastparse третий проход занял ~18 минут против прогноза в сотни часов. Объёмы дерева: БП 3.0 (818 МБ) → 127 764 файла; УТ 11.5 (883 МБ) → 68 177 файлов, 3,5 ГБ.

## Крупные `.cf` — эксплуатация

- **Сколько весит:** БП 3.0 (818 МБ) → 127 764 файла; УТ 11.5 (883 МБ) → 3,5 ГБ дерева. Temp в пике — ещё столько же и больше: результат класть на диск с запасом в 5–10 раз больше исходного `.cf`.
- **Temp:** проверять, что `tmpXXXX` реально появился на указанном диске.
- **Лимит нагрузки:** серийный режим — один поток плюс приоритет `BelowNormal`, машина остаётся отзывчивой. Пик памяти 2.0.0 на УТ 11.5 — около 1 ГБ (вероятно, из-за разбора в памяти вложенных контейнеров и крупных файлов; у 1.0.0 на УТ не замерялся).
- **Долгий прогон запускать отделённо** — фоновые задачи среда гасит при нехватке памяти. Надёжнее через WMI, процесс не наследует дескрипторы сессии:
  ```
  Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine='cmd /c "python tools\run_unpack.py <src> <out> <temp> > out.log 2> err.log"'}
  ```
  `Start-Process -RedirectStandardOutput/Error` тоже переживает остановку задачи, но запускающая команда висит, пока жив дочерний процесс. Мониторить по лог-файлам, стек смотреть `py-spy dump --pid <PID>`.
- **Зашифрованный zip** распаковывать 7-Zip (`7z x <архив> -o<папка> -p<пароль>`): питоновский ZipCrypto даёт около 40 МБ/мин, 7-Zip — секунды.

## Правила

- **Не передавать при распаковке:** `--descent` (замедляет до зависания, контент тот же) и `--version` (нужен лишь в редких случаях декомпиляции, а при сборке `.epf` ломает результат).
- Изменение структуры форм и метаданных — только Конфигуратор или EDT; v8unpack меняет только BSL и текст.
- **Имена файлов зависят от версии v8unpack:** 1.2.6 писала `CommonModule.obj.100.bsl` и `ConfigurationExtension.100.json`, 1.2.13 — без `.100`. Старые и новые деревья по путям напрямую не сравниваются.
- **`dummy.zip`** (второй контейнер `.cf`) v8unpack пересобирает при каждой распаковке: содержимое то же, время в записях архива — нет. Деревья сравнивать с учётом этого (`bench/scripts/compare_tree.py`).
- После обновления v8unpack: `v8unpack_fastparse_check.py` на 400 файлах `decode_stage_1` — 0 расхождений, затем полная распаковка контрольного файла и сравнение дерева.

## Fallback для крупной/проблемной конфигурации — Конфигуратор
```
"<каталог 1cv8>\bin\1cv8" CREATEINFOBASE File="<путь_ИБ>"
"<каталог 1cv8>\bin\1cv8" DESIGNER /F "<путь_ИБ>" /LoadCfg "<файл.cf>" /DumpConfigToFiles "<папка>"
```
Робастнее v8unpack, но тяжелее (загрузка конфигурации в ИБ + выгрузка). Для расширений — с ключом `-Extension <Имя>`.
