# Реестр патчей v8unpack-accel 2.0.0

Основа — поставка 1.0.0 (`../v1.0.0/tools`), она не изменялась. Патчи — unified diff
(`git diff --no-index --no-prefix`), пути от корня поставки (`tools/...`), UTF-8, переводы строк как в файлах
(CRLF у `v8unpack_serial.py` и `run_unpack.py`, LF у остальных). Порядок и sha256 — `patches/series.json`,
хеши всех файлов — `MANIFEST.json`. `python ../verify_release.py --replay` применяет серию к 1.0.0
во временном каталоге (`git apply`) и сверяет результат с `tools/` побайтно.

Пакет v8unpack (1.2.13) не патчится: все изменения — модули-обёртки, которые подменяют методы во время запуска.
Модули 001–006 содержат изменённые копии функций v8unpack (MIT, Copyright (c) 2015 infactum),
источник указан в шапке каждого.

## 001 — значения вне кавычек куском

`fast_decode_object`: в режиме `READ_PARAM` подряд идущие обычные символы берутся одним куском до ближайшего
`,` `}` `"` или перевода строки (регулярное выражение), а не по символу. Кусок не содержит `}`, поэтому
сравнение `previous_char == '}'` в `_end_value` работает как раньше. Члены `Mode` взяты в константы модуля:
доступ `Mode.X` через класс в Python 3.11 идёт через дескриптор перечисления.
Проверка: `v8unpack_fastparse_check.py` против исходного автомата. Корневой файл конфигурации 640 КБ:
0,453 → 0,031 с.

## 002 — склейки строк через список

`decode_b64_line`, `_decode_line_read_text_file`, многострочные значения — строка отвязывается от атрибута
перед `+=`. `OrganizerCode.unpack` копил модуль в `self.code_areas[k]['data'] += line` (строка в словаре —
полная копия на каждую строку модуля); теперь куски копятся в списках и склеиваются один раз, ключи и порядок
областей те же. Тело разбора вынесено в `split_code_areas(cls, file, file_name)` — его использует 006.
Замер: 8 модулей УНФ 0,3–3,2 МБ — 51,3 → 0,17 с CPU; текстовый файл 102 МБ больше не встаёт.

## 003 — разбор скобочного формата через json.loads

`decode_file` читает файл целиком и переводит скобочный текст в JSON операциями уровня C:
- `split('"')` делит текст на части «вне» и «внутри» строк по чётности кавычек;
- цепочка `str.replace` расставляет скобки и кавычки значений;
- `translate` переводит служебные символы в `[`, `]` и `"`.

Разбирает `json.loads`. Правила автомата и особые случаи (base64, текстовые файлы, многострочные значения,
пустое значение после `}`) описаны в шапке модуля. Всё, что не укладывается в правила, уходит в исходный
автомат через толерантный `decode_file`. Так же уходит BigBase64 — он определяется по двум первым строкам,
не дочитывая файл.

Сверки:
- против исходного `JsonContainerDecoder` — 400 случайных файлов `decode_stage_1` УНФ, 0 расхождений;
- три тяжёлые формы 1,5–2 МБ — совпали; исходный разбор 537, 12,2 и 10,2 с CPU, новый — 0,08–0,11 с;
- против цепочки 1.0.0 + прототипов — 11 130 файлов двух распаковок УНФ, 0 расхождений, разбор в 2,8–5,5 раза быстрее.

## 004 — запись JSON своим сериализатором

`helper.json_write` через `dumps`: рекурсия по спискам и словарям в один список кусков, строки кодирует
C-функция `json.encoder.encode_basestring`, файл пишется одной записью. Формат побайтно как у
`json.dump(indent=2, ensure_ascii=False)`. Типы вне str/list/tuple/dict/None/bool/int уходят в штатный `json.dumps`.
Сверка: 4060 JSON-файлов выгрузки УТ 11.5 (216 МБ) — 0 расхождений; CPU 11,4 → 4,2 с, с записью 19,9 → 7,6 с.
Действует и при сборке (`build`).

## 005 — вложенные контейнеры в памяти, кэш каталогов

`decompress_file_and_extract`: вложенный контейнер копится в памяти и разбирается из `BytesIO`. Штатно он
проходил цикл «запись → `os.rename` в `.temp` → чтение → удаление»: четыре файловые операции, а `os.rename`
сразу после записи — источник WinError 32. Цикл распаковки и условие остановки те же, пустой источник даёт
пустой файл, как в оригинале. `Container.extract_file` при `recursive=True` определяет контейнер по байтам
в памяти, не открывая записанный файл заново; верхний уровень `.cf` пишется потоком, как раньше.
`helper.makedirs` запоминает созданные каталоги; кэш сбрасывается в `helper.clear_dir` — единственном месте,
где v8unpack удаляет каталоги до конца распаковки — и при переносе каталога в 006.

## 006 — организатор без копирования

Без `index` и `descent` дерево результата повторяет `decode_stage_3`, поэтому `decode_stage_3` переносится
в каталог результата одним `os.replace`. На месте обрабатываются только `.bsl` и `.elem.json`, обход идёт
через `os.scandir`. Файл, который организатор записал бы теми же байтами, не перезаписывается:
- `.bsl` — результат сравнивается с исходными байтами (с учётом перевода строк при записи);
- `.elem.json` без областей `include_`/`includr_` — организатор записал бы тот же `json_write` тех же
  данных, файл не трогается.

Другой том, неудачный перенос, `index` или `descent` — штатный путь с копированием.
`v8unpack_resume.py` не ломается: он заново строит `decode_stage_3` из `decode_stage_1`.
Замер: организатор УТ 11.5 — 29 мин (1.0.0, журнал) → 31 с.

## 007–009

- `v8unpack_serial.py`: `__version__ = "2.0.0"`, `FEATURES`, `V8UNPACK_DISABLE`, порядок подключения
  (fastbrace — после толерантного `decode_file`), `banner()`, ссылка на гайд `docs/raspakovka-v8unpack.md`.
- `v8unpack_fastparse_check.py`: эталон — исходные методы `JsonContainerDecoder`, снятые до импорта
  `v8unpack_serial`, плюс толерантный `decode_file`. Проверяется вся цепочка разбора, каталог обходится
  рекурсивно, CPU считается по `process_time`, код возврата 1 при расхождениях.
- `run_unpack.py`, `v8unpack_resume.py`: строка версии и набора ускорений в выводе, пути в примере
  отделённого запуска — плейсхолдеры.

## Что не патчилось

Пакет v8unpack, контейнерный формат верхнего уровня (`container_extract`), сборка контейнера (`build`,
кроме `json_write` и кэша каталогов), режимы `index` и `descent` (`OrganizerFileCE`), параллельный пул —
серийный режим остаётся единственным.
